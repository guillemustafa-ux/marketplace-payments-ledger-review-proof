# marketplace-payments-ledger-review-proof

An independent code review of a synthetic marketplace payments backend that anyone can re-run
offline. The backend ships in two versions: **v1** with nine planted money defects and **v2** with
each of them fixed. A review suite finds each defect on v1 with a failing spec, confirms the same
spec passes on v2, and writes a sample report ([`SAMPLE_REPORT.md`](SAMPLE_REPORT.md)) with
severity, location in the code, the observed numbers, the suggested fix and the retest result.
"Fixed" means the specs below pass on v2. The rules they do not pin, and the known gaps, are listed
under [Limits](#limits).

Everything runs against a real Postgres (started with `embedded-postgres`), a fake provider that
speaks HTTP on a random port of `127.0.0.1`, and a webhook harness that signs Stripe-shaped events.
There are no mocks of the database, no web framework (plain `node:http`) and nothing leaves
`127.0.0.1` at test time.

## What it proves

1. **Each defect is found.** Every finding has one spec that states the correct behaviour with exact
   numbers. On v1 exactly the finding specs fail and nothing else does (`npm run review` requires it).
2. **Each defect is fixed.** The same specs pass on v2, and the controls pass on both versions.
3. **The suite bites.** Each footgun reverts one v2 fix in a temporary copy of the source and
   passes only when exactly the specs named for it in [`footguns/manifest.json`](footguns/manifest.json)
   go red and every other spec stays green. Every footgun names its own finding's spec; `f2` also
   names F7's and `f4` also names F5's (see below).

The numbers and locations in the generated blocks below come from
[`scripts/readme.mjs`](scripts/readme.mjs) and are checked by `npm test`; none of them is typed by
hand.

## The domain

Fans pay for private chats with creators. Amounts are integer cents, USD only.

- On capture the platform fee is 20 % (rounded half up to the cent), the creator gets the remainder,
  and a referral reward of 10 % of the fee (rounded down) goes to the creator's referrer, paid out of
  the fee.
- Refunds can be full or partial, and one charge can be refunded in several parts. Each refund
  moves money once, from its `refund.created` event, keyed by the refund id. `charge.refunded` is
  accepted but moves no money (see [`docs/sources.md`](docs/sources.md)).
- A refund is split against the running total already reversed on the charge: creator, referrer
  and platform each give back the difference between their share of the total after this refund
  and before it, so the parts of a full refund add up to exactly what the capture paid each party.
- A dispute is reversed the same way, across creator, referrer and platform in one ledger
  transaction. Every reversal is capped at what is left of the charge, so a dispute for the full
  charge takes back whatever earlier refunds left.
- Creators withdraw through payouts.
- The ledger is double entry: every ledger transaction sums to zero.

Invariants every version tries to keep:

- **I1** every ledger transaction balances.
- **I2** each (provider object id, entry type) produces at most one ledger transaction.
- **I3** after a charge is refunded in full, in one part or several, every balance derived from
  that charge is zero.
- **I4** the daily reconciliation flags any difference, per creator, between the creator earnings
  from captures in the ledger and at the provider.

The webhook signature (`t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<raw body>">`, verified over the raw
body) is checked in both versions. It is a control, not a defect.

## Re-run it

Node 22.12+, 24 or 26+ (the range vitest declares, repeated in `engines`; developed on Node 24). No
Docker, no database to install, no API key.

```bash
npm ci
npm test
npm run review
```

Also available:

```bash
npm run typecheck
npm run footgun -- --all
npm run footgun -- f1
npm run readme
```

`npm test` runs every spec on v2 and the controls on v1. It then checks the README's generated blocks
and, in the sample report, the verdict line and each finding's title, severity, location, spec and
fix. `npm run review` runs the specs on v1 (exactly the finding specs must fail), then on v2
(everything must pass), and rewrites `SAMPLE_REPORT.md`. The observed numbers in the report are
checked only by re-running it: CI does, and fails if the committed report changes. The specs read `TARGET=v1|v2` from the environment (unset
means v2; any other value is an error).

Each run starts its own Postgres in a fresh directory under the OS temp folder and removes it
afterwards. If `DATABASE_URL` is set, the tests use that server instead, in a new throwaway database.

A footgun copies `src` and `test` to a temporary directory, links the real `node_modules` into it,
applies its edits there (see [`footguns/edits.mjs`](footguns/edits.mjs)), runs the suite with
`TARGET=v2`, and deletes the copy. The working tree is never modified.

F1 and F2 overlap. F2's fix (one ledger transaction per provider object id and entry type) already
stops a redelivered event from crediting twice, so on v2 F1's fix (the event id stored under a unique
constraint) is a second line of defence with no money effect of its own, which is why F1 is Medium.
On v1 both are open, so a redelivery doubles the credit. The F1 spec also asserts that the event id
was stored once: that is the property only F1's fix adds, and the only thing its footgun breaks. It
checks the stored row, so code that stores the event id and still processes the duplicate would pass
it; with F2's key in place such code has no money effect.

Two footguns also turn a second spec red. `f2` breaks F7: F7 repeats a capture request for the same
order after a restart, the provider returns the same charge for the stored idempotency key, and
without F2's key the ledger records that charge twice. `f4` breaks F5: F5 checks that a charge refunded in three parts
ends at zero for every party, and with refunds keyed by the charge id only the first part is applied.

## Layout

```text
src/common/        fake provider, db helpers, webhook signing, HTTP shell, math, v2 schema
src/v1/            ledger with the planted defects, and its (weaker) schema
src/v2/            ledger with the fixes
test/spec.test.ts  the specs, parameterised by TARGET
test/support/      embedded Postgres setup and the harness (provider + app + signed webhooks)
scripts/           test, review, footgun, readme and the shared helpers
footguns/          manifest and the edits each footgun applies
docs/sources.md    the Stripe sentences the faults rely on, with URL and UTC date
SAMPLE_REPORT.md   the sample report written by npm run review
```

v1 also has a weaker schema: no event table, no unique key on ledger transactions, and no tables for
applied reversals, parked reversals, capture intents or payout intents. That is part of what the
review finds.

## Limits

- **Synthetic data.** There are no real users, creators, amounts or providers.
- **Never run against Stripe, MassPay or any real provider.** Every call goes to a fake provider on
  `127.0.0.1`.
- **No production use.** This is a review exercise, not a payments library.
- **Stripe Connect Accounts v2 and MassPay are not modelled.** One currency (USD) only.
- **Behaviour is grounded only in the quoted documentation sentences** in
  [`docs/sources.md`](docs/sources.md). Everything else below is an assumption.

What the specs do not pin. They cover the nine findings and four controls. These v2 rules are
implemented, but no spec would fail if they broke:

- the cap on a reversal at what is left of the charge (an over-refund);
- applying several parked reversals for one charge;
- I1 and I2 as general properties (they are checked only through the balances and transaction
  counts the specs assert);
- reconciliation of anything but capture earnings, and of a creator present on only one side.

Known gaps in v2:

- **Not safe under concurrent delivery.** v2 takes no lock per charge. Two reversals of one charge
  processed at the same time can read the same running total and together reverse more than the
  charge, and a reversal that races its capture can stay parked. A production version needs a
  per-charge lock. No spec covers concurrency.
- **A small reversal can move a cent between parties.** Creator and referrer shares of the running
  total are rounded down and the platform takes the remainder, so the platform's running share can be
  up to 2 cents above its exact proportion. One small reversal can move a cent between parties: on a
  1000-cent charge, a 1-cent refund after a 49-cent one takes 1 cent each from creator and referrer
  and gives 1 cent back to the platform. A full refund still ends at zero for every party.
- **Reconciliation day.** The ledger dates a webhook capture by the event's `created`, and the
  provider dates it by the charge's. An event delivered on a later day than its charge shows up as a
  reconciliation difference. The harness sends both with the same timestamp.

Assumptions, none of them stated in the fetched pages:

- The fee, referral and dispute rules, and the proportional split of a refund across creator, referrer
  and platform, are the exercise's domain rules.
- The fake provider's `POST /v1/captures`, `POST /v1/payouts` (with `client_reference`),
  `GET /v1/payouts?client_reference=...` and `GET /v1/reconciliation` are inventions. Only the
  idempotency-key semantics of captures follow the page.
- `charge.refunded` is accepted and ignored for money; every refund moves money from its own
  `refund.created` event, which the page points to for information about the refund. An endpoint
  that receives only `charge.refunded` would have to list the charge's refunds from the API; that is
  not implemented.
- A dispute reverses its amount, capped at what is left of the charge, split like a refund. Dispute
  fees, a won dispute and reinstated funds are not modelled. The page says only when the event occurs.
- Payouts are driven through the provider endpoints, not through `payout.paid` or `payout.failed`
  events. A payout whose intent is pending or unknown is resolved on the next request by looking it
  up by `client_reference`, and sent only when the provider has none; this assumes the lookup sees
  every payout the provider accepted. Two concurrent requests for one `client_reference` are not
  tested.
- The capture idempotency key is stored per `order_id` before the first send and reused on every
  retry and repeated request. Key expiry on the provider side is not modelled.
- F2 is modelled as two `charge.succeeded` events with different ids for one charge.
- F3 is fixed by parking an early refund or dispute and applying it when the capture is recorded.
  The other option the page mentions, retrieving the object from the API, is not implemented.
- The signature check accepts any of the `v1=` signatures in the header, compared in constant time,
  and does not enforce a timestamp tolerance; the harness signs with fixed timestamps.
- Retries are capped at a fixed attempt count that no spec exercises, and there is one Postgres with
  no replicas.
- The CI workflow in [`.github/workflows/ci.yml`](.github/workflows/ci.yml) has not been run: nothing
  here was pushed, so neither the Linux nor the Windows job is verified.
