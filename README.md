# payments-ledger-review-proof

An independent code review of a synthetic marketplace payments backend that anyone can re-run
offline. The backend ships in two versions: **v1** with planted money defects and **v2** with
every one of them fixed. A review suite finds each defect on v1 with a failing spec, confirms the
same spec passes on v2, and writes a redacted sample report ([`SAMPLE_REPORT.md`](SAMPLE_REPORT.md))
with severity, location in the code, the observed numbers, the suggested fix and the retest result.

Everything runs against a real Postgres (started with `embedded-postgres`), a fake provider that
speaks HTTP on a random port, and a webhook harness that signs Stripe-shaped events. There are no
mocks of the database, no web framework (plain `node:http`) and no network at test time.

## What it proves

1. **Each defect is found.** Every finding has one spec that states the correct behaviour with exact
   numbers. On v1 exactly the finding specs fail and nothing else does (`npm run review` requires it).
2. **Each defect is fixed.** The same specs pass on v2, and the controls pass on both versions.
3. **The suite bites.** Each footgun reintroduces one v2 fix in a temporary copy of the source and
   passes only when exactly the spec named in [`footguns/manifest.json`](footguns/manifest.json) goes red
   and every other spec stays green.

Numbers and locations below are generated by [`scripts/readme.mjs`](scripts/readme.mjs) and checked
by `npm test`; none of them is typed by hand.

## The domain

Fans pay for private chats with creators. Amounts are integer cents, USD only.

- On capture the platform fee is 20 % (rounded half up to the cent), the creator gets the remainder,
  and a referral reward of 10 % of the fee (rounded down) goes to the creator's referrer, paid out of
  the fee.
- Refunds can be full or partial. A dispute reverses the creator earnings and the referral reward.
  Creators withdraw through payouts.
- The ledger is double entry: every ledger transaction sums to zero.

Invariants every version tries to keep:

- **I1** every ledger transaction balances.
- **I2** each (provider object id, entry type) produces at most one ledger transaction.
- **I3** after a full refund of a charge every balance derived from that charge is zero.
- **I4** the daily reconciliation flags any difference in amount per creator between the ledger and
  the provider.

The webhook signature (`t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<raw body>">`, verified over the raw
body) is checked in both versions. It is a control, not a defect.

## Re-run it

Node 22.12 or later (declared in `engines`; developed on Node 24). No Docker, no database to install,
no API key.

```bash
npm ci
npm test
npm run review
```

Also available:

```bash
npm run typecheck
npm run footgun -- --all
npm run footgun -- f1
npm run readme
```

`npm test` runs every spec on v2 and the controls on v1, then checks the README. `npm run review`
runs the specs on v1 (exactly the finding specs must fail), then on v2 (everything must pass), and
rewrites `SAMPLE_REPORT.md`. The specs read `TARGET=v1|v2` from the environment.

Each run starts its own Postgres in a fresh directory under the OS temp folder and removes it
afterwards. If `DATABASE_URL` is set, the tests use that server instead, in a new throwaway database.

A footgun copies `src` and `test` to a temporary directory, links the real `node_modules` into it,
applies its edits there (see [`footguns/edits.mjs`](footguns/edits.mjs)), runs the suite with
`TARGET=v2`, and deletes the copy. The working tree is never modified.

The fix for F1 (event id stored under a unique constraint) and the fix for F2 (a ledger key on
provider object id and entry type) overlap: with F2's key in place a redelivered event no longer
credits twice even without F1's fix. The F1 spec therefore also asserts that the event id was stored
once, which is the property F1's fix adds and the only thing its footgun can break.

## Layout

```text
src/common/        fake provider, db helpers, webhook signing, HTTP shell, math, v2 schema
src/v1/            ledger with the planted defects, and its (weaker) schema
src/v2/            ledger with the fixes
test/spec.test.ts  the specs, parameterised by TARGET
test/support/      embedded Postgres setup and the harness (provider + app + signed webhooks)
scripts/           test, review, footgun, readme and the shared helpers
footguns/          manifest and the edits each footgun applies
docs/sources.md    the Stripe sentences the faults rely on, with URL and UTC date
SAMPLE_REPORT.md   the redacted sample report written by npm run review
```

v1 also has a weaker schema: no event table, no unique key on ledger transactions, no parking table
for early refunds and no payout intents table. That is part of what the review finds.

## Limits

- **Synthetic data.** There are no real users, creators, amounts or providers.
- **Never run against Stripe, MassPay or any real provider.** Every call goes to a fake provider on
  `127.0.0.1`.
- **No production use.** This is a review exercise, not a payments library.
- **Stripe Connect Accounts v2 and MassPay are not modelled.** One currency (USD) only.
- **Behaviour is grounded only in the quoted documentation sentences** in
  [`docs/sources.md`](docs/sources.md). Everything else below is an assumption.

Assumptions, none of them stated in the fetched pages:

- The fee, referral and dispute rules, and the proportional split of a refund across creator, referrer
  and platform, are the exercise's domain rules.
- The fake provider's `POST /v1/captures`, `POST /v1/payouts` (with `client_reference`),
  `GET /v1/payouts?client_reference=...` and `GET /v1/reconciliation` are inventions. Only the
  idempotency-key semantics of captures follow the page.
- `charge.refunded` is read as carrying the refunded total in `amount_refunded`. The page says only
  that the event carries the charge, including partial refunds.
- A dispute is treated as a full reversal of the charge. The page says only when the event occurs.
- Payouts are driven through the provider endpoints, not through `payout.paid` or `payout.failed`
  events. The provider can fail a payout first and queue the failure for later, but no spec uses that
  fault.
- F2 is modelled as two `charge.succeeded` events with different ids for one charge.
- F3 is fixed by parking the early refund. The other option the page mentions, retrieving the object
  from the API, is not implemented.
- The signature check does not enforce a timestamp tolerance; the harness signs with fixed timestamps.
- Retries are capped at a fixed attempt count that no spec exercises. Concurrent webhook delivery is
  not tested, and there is one Postgres with no replicas.
- The CI workflow in [`.github/workflows/ci.yml`](.github/workflows/ci.yml) has not been run: nothing
  here was pushed. An embedded Postgres failing to initialise on a hosted Windows runner has been seen
  in a sibling project, so that job is unverified.
